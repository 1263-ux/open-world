# Open World · 太理校园世界：时间线、Agent 团队与验收

> Draft 0.1 · 建议周期：4 周 MVP + 1 周缓冲。以可运行成果为准，不以 Agent 产出的代码行数为准。

## 1. 目标与 MVP 完成定义

交付一个可访问的 Web 3D 校园原型，包含虎峪、迎西校区、可辨识地标、校园探索交互、至少一个小游戏/任务、部署地址、测试报告与资源授权记录。

完成标准：
- 可启动、可构建、可部署。
- 两个校区可切换，主要道路和重点建筑位置关系基本合理。
- 可旋转/缩放/拖动视角，点击地标显示信息。
- 至少一个玩法可以开始、完成、重玩、退出。
- 桌面端主路径通过 Playwright；手机端完成基础可用性检查。
- 第三方资源均有来源与许可记录。
- README、架构说明、已知问题和 API 消耗记录齐全。

## 2. 四周时间线

### 第 0 阶段：启动与约束（第 1-2 天）
任务：
- 检查仓库，创建 `AGENTS.md`、目录结构、Issue 模板和 CI。
- 收集官方校区图、照片，建立资源来源清单。
- 审查 Hks 的运行方式与授权，不预设可以直接复制。
- 定稿低多边形风格、色板、镜头和资产命名规则。

验收：
- 新环境可安装依赖、启动开发服务器并完成构建。
- 技术决策记录、资源清单已建立。
- 一张视觉基准图/截图和场景坐标约定获项目负责人确认。

### 第 1 周：3D 技术验证与场景骨架
任务：
- Vue + Three.js 场景启动、相机控制、灯光、地面、道路和基础树木。
- 导入测试 GLB，验证加载、点击拾取和资源清理。
- 用简化体块搭出两个校区的空间骨架。
- 配置 lint、typecheck、test、build 与 GitHub Actions。

验收：
- 新环境按 README 可运行。
- 两校区可切换，地标点击能触发 UI。
- CI 通过；记录首屏加载时间、构建体积和目标设备表现。

### 第 2 周：校园建模与信息系统
任务：
- 校准道路、建筑占地、绿地和主要出入口。
- 制作 3-8 个代表性建筑的 L2 模型，其他建筑使用 L0/L1。
- 建立地标 JSON、信息卡片、搜索/定位或分类筛选。
- 实现模型按需加载。

验收：
- 两个校区的空间布局可辨识。
- 重点建筑有来源依据，未知信息有标记。
- 模型命名、格式、大小和许可证检查通过。

### 第 3 周：玩法与 Hks 集成试验
任务：
- 实现地标打卡/校园寻宝等一个完整任务循环。
- 在独立分支验证 Hks 的启动、授权、路由/iframe 方案和性能。
- 若授权或技术验证不通过，改用自制小游戏，例如路线寻宝、记忆配对或校园知识问答。
- 加入开始、完成、重玩、返回校园和失败提示。

验收：
- 至少一个玩法从入口到完成再返回地图全流程可用。
- Hks 未通过许可门禁时，不得复制其代码或素材；替代玩法仍必须交付。
- 游戏不会破坏主场景状态，异常时可返回校园。

### 第 4 周：性能、测试与发布
任务：
- Playwright 覆盖校区切换、地标点击、任务开始/完成/退出。
- 修复资源泄漏、移动端布局、加载错误与键鼠操作问题。
- 检查资源许可证、API 支出、README、部署与回滚流程。
- 发布 MVP，收集 3-5 位真实用户的可用性反馈。

验收：
- 构建与自动化测试通过，未解决问题列入清单。
- 部署地址可用，提供截图/短录屏与测试报告。
- API 总支出不超过 $90，资源来源清单无未审批资产。

### 第 5 周：缓冲与体验打磨（可选）
只处理高优先级问题：地图校准、重点建筑辨识度、加载性能和用户反馈。不得未经讨论扩张到多人系统或大规模室内建模。

## 3. Agent 团队设计

建议采用“一个主控 + 4 个专业 Agent + 人类负责人”的轻量模式。不要创建十几个 Agent 然后让它们互相开会，最后没人交付。

### 角色
1. **Product/Orchestrator Agent（主控）**
   - 把需求拆成 Issue，维护依赖、优先级、阶段目标。
   - 为子任务定义文件范围、验收标准和测试命令。
   - 汇总报告，不直接包办所有实现。

2. **Campus Research Agent（校园资料）**
   - 收集官方地图、建筑照片、名称和来源。
   - 输出结构化 `campus-landmarks.json` 草案与来源表。
   - 不确定的事实标记 `unverified`，禁止编造。

3. **3D Scene Agent（场景与模型集成）**
   - 负责 Three.js 场景、相机、灯光、GLB 加载、点击拾取和性能。
   - 不擅自重写 UI 状态层。
   - 提交截图、模型大小和性能记录。

4. **Frontend/Product UI Agent（界面与玩法）**
   - 负责校区切换、信息卡片、任务流程、小游戏入口与返回。
   - 通过 `GameRegistry` 接入玩法，不把游戏逻辑塞进场景循环。

5. **QA/Reviewer Agent（测试与审查）**
   - 审查 diff、运行 lint/typecheck/test/build。
   - 检查主要用户路径、资源泄漏、许可证清单和 API 预算。
   - 不替实现 Agent 默默修完所有问题；先报告可复现问题，再分配修复任务。

### 人类负责人职责
- 决定视觉风格、优先级、资源授权与是否合并。
- 评审每个阶段演示，批准预算例外。
- 不接受“代码写完了”作为验收，只接受可运行、可验证的结果。

## 4. Agent 工作协议

每个任务必须提供：
- 目标与非目标；
- 允许修改的目录/文件；
- 输入资料和证据链接；
- 验收标准；
- 必跑命令；
- 预期输出（代码、截图、报告或模型）；
- 风险和未完成事项。

每个任务结束后，Agent 必须汇报：
1. 改了什么；
2. 如何验证；
3. 测试结果；
4. 新增/使用的资源及许可证；
5. API 预算估算；
6. 已知问题；
7. 建议的下一步。

## 5. Git 与协作规则

- `main` 始终保持可构建；功能使用短分支。
- 每个阶段至少一个可审查 commit；复杂功能使用 PR。
- 不允许多个 Agent 同时修改同一个关键文件；主控负责分配文件边界。
- 合并前由 QA Agent 给出测试结果，人类负责人决定是否合并。
- 不把大体积原始地图、未授权素材、密钥或个人照片直接提交到仓库。
- CI 失败不允许标记阶段完成。

## 7. 阶段验收总表

| 阶段 | 必须交付 | 通过条件 |
|---|---|---|
| 启动 | AGENTS.md、资源表、技术决策、CI | 本地启动与构建通过 |
| 第 1 周 | 3D 骨架、相机、地标点击 | 双校区切换、点击可用 |
| 第 2 周 | 地图布局、重点建筑、信息卡 | 布局可辨识、事实可追溯 |
| 第 3 周 | 一个完整玩法、Hks 审查结论 | 游戏循环完整，许可门禁通过 |
| 第 4 周 | 自动化测试、部署、报告 | 主路径通过、预算合规 |
| 缓冲周 | 高优先级体验修复 | 问题闭环，不扩张范围 |

## 8. 风险清单

- **范围膨胀：** 先保证两个校区可探索，再扩建筑与玩法。
- **地图授权不清：** 官方图优先用作建模参考；公开展示/分发前确认使用边界。
- **Hks 无明确许可：** 未确认前仅审查和本地运行，不复制代码/素材；准备自制玩法兜底。
- **模型过重：** 低面数、按需加载、纹理压缩，按设备实测。
- **Agent 并行冲突：** 文件所有权、短分支、PR 审查。
- **API 预算失控：** 预算阈值、阶段记账、停止条件。
